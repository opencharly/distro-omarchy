# 2026.242.1725 — feat(vm): omarchy-vm — the official ISO, installed unattended

## Summary

Adds **`omarchy-vm`** — the faithful Omarchy VM. It boots Omarchy's own official installer
ISO rather than reconstructing the distro from packages, so what you get is what Omarchy's
authors ship: limine + a UKI, btrfs `@`/`@home`/`@log`/`@pkg`, snapper, sddm + uwsm. Charly
supplies only the answers.

**This entity has installed a real Omarchy guest.** Built from this repo, it fetched the
5.8 GiB ISO, rendered the seed, allocated a blank 40 GiB disk, and the resulting guest
installed unattended and booted to a working Hyprland desktop.

**Two files change, and both are in this PR:**

- `charly.yml` — the `omarchy-vm` entity **and** its `disposable: true` bed
  `check-omarchy-iso-vm`. The bed IS committed here and it passes; see below.
- `.github/workflows/deploy.yml` — the build gate cloned charly `v2026.241.1535`, which
  predates the `iso` VmSource arm and therefore rejected the very entity this repo exists to
  ship (`source.kind: conflicting values "clone" and "iso"`). Bumped to `v2026.242.1422`,
  which pins spec `v0.2026242.1251` (the `iso` arm) and plugin-vm `v0.2026242.1323` (the iso
  build engine). That is a gate testing the manifest against a schema older than the manifest,
  not a defect in the manifest.

## Three fields that are load-bearing, each learned by building

**`checksum: {type: sha256}` with no value.** The publisher serves a `.sha256` sidecar,
which the fetcher auto-resolves. Pinning a literal would go stale on every point release
while the sidecar cannot. Verified: the fetch verified against the sidecar with nothing
authored.

**`ssh_authorized_key` deliberately absent**, so it defaults to the public half of
`ssh.key_source: generate`. That default is what makes the guest reachable at all — a stock
Omarchy install ships openssh with the service **disabled** and the port **closed**, and the
installer treats an `authorized_keys` file on the seed as the instruction to enable sshd and
open the firewall. Naming a key here would silence the default without saying so.

**The display block is required, not decorative.** Omarchy's installer runs in a graphical
session on the ISO's live environment. Measured: a domain with no video device boots the
medium and runs cloud-init against the seed, then sits idle with the disk untouched.

`user`/`user` with `encrypt: false`, and that pairing is the point: an encrypted install is
**not fully unattended** (someone types the LUKS passphrase at first boot) and its
passphrase would sit in **plaintext** in the seed's `disk_encryption` block, making this file
a secret. With `encrypt: false` there is no such block and nothing on the seed that is not
already public.

## Two schema corrections the draft got wrong

Both caught by `charly box validate`, both worth knowing before the next VM entity is
authored:

- **a `kind: vm` node takes no `description:`**
- **`network:` is a struct, not a string**

The first is the nastier one: an unknown `description` knocks the node out of the `vm`
disjunction entirely, and the error CUE then reports names `network` — pointing at a field
that is perfectly correct.

## What is deliberately not here

`omarchy-pacstrap-vm` needs an `omarchy-pacstrap-builder` box, which needs `limine` added to
`layer-pacstrap-builder` first — the bootloader install runs **inside** the builder container
against the mounted target, so the binary must exist there, not only in the target rootfs.
An entity naming a builder box that does not exist would not validate. Named in the file, not
silently skipped.

### The bed asserts as an unprivileged user, and that made it stronger

Every check runs as the `user` the installer created — the only account the seed authorizes.
Two assertions had to be rewritten because of it, and both got **stronger**, not weaker:

| Was | Why it could not work | Now | Why it proves more |
|---|---|---|---|
| `btrfs subvolume list /` | needs CAP_SYS_ADMIN — fails as `user` with *"can't perform the search: Operation not permitted"* | `findmnt` at each of the four mountpoints | a subvolume can exist while mounted nowhere; this asserts the layout the answers actually asked for |
| `test -f /boot/limine.conf` | the installed ESP is mode `0700 root root`, so this is a permission denial and **not evidence about limine at all** | `efibootmgr`, matching `BootCurrent` to the Limine entry | proves `limine_x64.efi` is ON the ESP, a boot entry names it, **and this boot came from it** |

That is the opposite of weakening a bed to make it pass: the two failing checks were **the
bed's own defects**, asserting root-only facts as a non-root user.

### The two product defects this bed found

It did not pass on the first attempt, and what it caught was real:

1. **The managed ssh stanza has two writers.** `vm create` publishes it correctly for an
   installer-ISO guest (`UserKnownHostsFile /dev/null`), and `plugin-deploy-vm`'s
   `prepare-venue` overwrote it with a real `known_hosts` path. The guest changes SSH host
   identity exactly once when it reboots out of the live installer, so a key recorded before
   that strands it and the readiness gate burns its whole cap — `[update] FAIL after
   13m11.524s`, reproduced twice. Fixed by `opencharly/plugin-vm#12` +
   `opencharly/plugin-deploy-vm#7`; the run above needs both.
2. **`install_timeout` was a dead field**, removed from the schema by `opencharly/spec#84`,
   and this repo still authored it — which is why its build gate was red. Dropped here.

### A third condition, named rather than parked

`sudo -n` in the installed guest fails with `sudo: a password is required`: a stock Omarchy
install grants password-required sudo. That is `opencharly/plugin-deploy-vm#6`, measured
there. It only bites a deploy that installs packages, and this bed installs none — which is
why it passes 13/13 with that condition present, and why the bed does not silently depend on
an unmerged fix.

### One correction this investigation produced

An earlier revision of this body blamed an unimplemented `source.install_timeout` for the bed
not completing. That was wrong twice over: my own exit-file waiter matched a stale file, so I
tore the guest down mid-run and read the resulting 30-minute poll as a timeout; and
`waitReady()` is best-effort with its return discarded, so it cannot fail a bed at all.
`install_timeout` turned out to be a dead field and was removed from the schema entirely by
`opencharly/spec#84`. This entity therefore does not author it — an earlier commit on this
branch did, which is why the branch's build gate was red before the pin bump; it does not
appear in the net diff.


## Rulebook compliance

- **R1 — RCA every anomaly.** The install stall was chased to a named root cause — the ISO's
  own `omarchy-cidata-load` losing a udev race against a SATA cdrom — after eliminating five
  hypotheses with evidence. Fixed at the source (sdk#197, plugin-vm#9), not described as
  flaky. #4 carries the full trail.
- **R2 — Finish the whole cutover.** The ISO template is complete. `omarchy-pacstrap-vm` and
  the `charly-omarchy` keeper deploy are named in the file with the concrete blocker
  (`limine` in `layer-pacstrap-builder`) rather than left implicit.
- **R3 — No duplication.** The entity re-declares nothing: source format from the distro,
  rendering from sdk, geometry from the distro's `installer:` block.
- **R4 — No workarounds.** No sleeps and no retries. Two workarounds were available and both
  rejected: weakening the bed until it passes on an uninstalled guest, and documenting "run
  the installer by hand a minute after boot" instead of fixing the race.
- **R5 — Delete legacy completely.** N/A — nothing is replaced; this is a new entity.
- **R6 — Git safety.** `git status` inspected before the commit; a single file, no
  force-push, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** The proof is a completed install and a desktop
  logged into, not a validate pass.
- **R8 — Preserve emitted artifacts.** The emitted artifacts (the seed volume, the blank
  disk) were inspected at their real boundary with `isoinfo`, `blkid` and `qemu-img info`,
  and the seed was accepted by Omarchy's own loader.
- **R9 — Binary equals source.** The install proof was taken on a binary carrying what were
  then unmerged branches. **Both have since merged** — charly#485 (the omarchy `installer:`
  block) and plugin-vm#8/#9 (the `iso` engine and the virtio answers volume) — so a binary
  built with `task build:binary` from published pins now renders this entity's seed. The one
  piece still unmerged is plugin-vm#10, which affects only the per-domain deploy path, not
  the direct `vm build`/`vm create` this entity's proof used.
- **R10 — Fresh disposable proof.** `check-omarchy-iso-vm` is `disposable: true` and reaches
  `PASS (steps=9)`, including `[update] PASS` (its own destroy-and-rebuild) and
  `[check-live-rebuild] 13/13` against the guest that rebuild installed from a blank disk —
  the output is quoted above. **Stated precisely, because it matters:** that run required two
  fixes the bed itself found, `opencharly/plugin-vm#12` and `opencharly/plugin-deploy-vm#7`.
  `#7` is merged; `#12` has a PASS verdict with auto-merge armed. Until `#12` lands, the run is
  reproducible with those two in place but not from a clean checkout of released deps alone —
  which is exactly why the attribution tier below is `analysed on a live system` and not the
  tier above it. Warnings on that run: `[update]` reported `warnings=1 allowlisted=5` and
  every other step `allowlisted=1` — all allowlisted, none introduced here.
