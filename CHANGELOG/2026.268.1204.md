## Summary

Adds the CONSUMER half of the console-install cutover: the Omarchy installer
KNOWLEDGE moves here, with Omarchy, as transport-neutral DATA. The generic
mechanism already landed (opencharly/sdk#276, opencharly/plugin-jetkvm#8,
opencharly/plugin-spice#11, opencharly/plugin-vm#41/#42, opencharly/charly-jetkvm#2,

**This cutover ships the PROVEN surface only**: the anchor mechanism, the entity
with the non-destructive `probe` recipe, and the live-verified JetKVM media
workflow. The `install`/`first_boot`/`ssh_setup` recipes and the destructive bed
are MOVED to the thematic batch (opencharly/distro-omarchy#58) — they cannot be
exercised live until the KVM's USB target is identified, and shipping an unproven
required gate is forbidden.

### `candy/omarchy-kvm-anchor` — the load-time anchor

A flat external `kind` needs a CANDY-level reference so `plugin-jetkvm` enters
the loader's scan closure: an `add_candy:`-only reference on a deploy node is NOT
seen by `connectDeclaredKindPlugins` (it scans with empty ResolveOpts), so the
word parses but the provider never registers and the entity is warn-skipped. This
candy carries the `plugin-jetkvm` ref (the `eval-pr`/`plugin-pipeline` pattern).

The candy is named `omarchy-kvm-anchor`, NOT `omarchy-kvm`, so it does not collide
with the ENTITY's top-level name in the flat namespace.

Its check is NON-VACUOUS by construction: it extracts ONLY the `candy:` list
block (`sed` between `^candy:` and `^plan:`) and greps for the ref there, so the
check's own command text — which lives in the `plan:` block, outside the
extracted range — cannot satisfy itself. Proven by mutation: with the ref line
removed the extracted block is empty and the check FAILS. (A same-file
`contains:` predicate would be vacuous, since the literal sits in the file it
reads.)

### `omarchy-kvm` (`kind: jetkvm`) — the probe recipe

The entity + the single-step, non-destructive `probe` recipe (wait for the
Omarchy wordmark, press F5). It proves the entity resolution, the recipe
selection, and the transport's input LIVE, on whatever screen the machine shows.
A one-step probe's broad anchor is deliberate: there is no next step to
desynchronise against (a multi-step wizard's anchors must be screen-unique).

### Moved to the batch (distro-omarchy#58)

- the `install` recipe — the archinstall configurator (greeter → keyboard → user
  form → timezone → review → disk → overwrite → `Installing Omarchy` → reboot);
- the `first_boot` recipe — the installed system's owner-provisioning wizard;
- the `ssh_setup` recipe — `omarchy-setup-security-sshd --key="{{ssh_pubkey}}"`
  (Omarchy's OWN command: installs openssh, enables sshd, `ufw limit 22/tcp`,
  authorizes the key), driven over a text TTY;
- the `answers`/`answers_env` maps (`OMARCHY_KVM_*`, `ssh_pubkey`);
- the destructive `check-omarchy-jetkvm-full-install` bed (JetKVM fetches +
  mounts the ISO, drives the recipes, ejects).

All recorded in `plan/omarchy-unified-console-install.md` §11–§12.

### Design carried into the batch (stated here for the record)

- **Power/boot is NOT a plan step**: a USB-only machine (a laptop) has no ATX/DC,
  so the operator powers it on and the greeter OCR gate synchronizes — never a
  fabricated power action.
- **`ssh_setup` uses Omarchy's own command**, not a hand-rolled sshd enable.
- **`install`/`first_boot` share the setup-form steps** (keyboard → … →
  timezone) because upstream's `install/provisioning/setup-form.sh` is the shared
  source both Omarchy wizards call — the duplication mirrors upstream's.

### The batch's blocker — the KVM's USB target is UNIDENTIFIED

The recipes moved to #58 cannot complete because HID input does not reach the
screen the KVM SHOWS:
- typing 40 characters at that Omarchy lock screen left its password field EMPTY
  (field-region AE == 0); `wake-host`, `ctrl+alt+F3`, `ctrl+alt+Delete`, a virtual
  USB device replug, and a full USB-emulation bus cycle changed nothing.
- Device side: `/sys/class/udc/ffb00000.usb/state = configured`, gadget
  `1d6b:0104` bound.
- Host side: the machine reachable as `qc` runs **CachyOS/KDE** (not Omarchy), its
  `card1-HDMI-A-1` is **disconnected**, and its screen is NOT the KVM's Omarchy
  lock screen — so `qc` is not the machine the KVM is wired to.

Root-caused from both ends. It is NOT "environmental / not this cutover's fault":
it is an unresolved topology fact (which machine is on the KVM's USB) that only
the operator can establish. Per strict-policy, the recipes that depend on it are
moved to the batch (#58) rather than shipped unproven.
