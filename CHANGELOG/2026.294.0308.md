# 2026.294.0308 — fix(skills): own the image-owned omarchy skill nodes from an omarchy-skills bundle candy (sdk#434)

## Summary

This PR re-homes this repo's image-owned `skill:` nodes onto one new `omarchy-skills` bundle candy, moves each body to that candy's `.agents/skills/<name>/SKILL.md` unchanged, and composes the bundle into every image that carries one of those skills.

**The defect.** `charly box validate` rejected these nodes with *"owner `<image>` is an image, not a candy — a `candy:` node carrying `base:` or `from:` folds into the image set, so it has no source directory and this skill's prose can never be read (it is also silently absent from the `ai.opencharly.skill` label)"*, citing [opencharly/sdk#434](https://github.com/opencharly/sdk/issues/434). The mechanism is structural rather than a missing search path: only a candy model carries a source directory, and the label projection keeps a skill only when its owner is in the image's composed candy chain — so an image-owned node is invisible to the label, not merely unreadable. Re-homing it is therefore the change that makes it reach the label for the first time.

**Why a new candy, and why that is not scope creep.** This is step 2 of the operator's ruling on that issue (step 1, the enforcement, is merged as opencharly/plugin-box#58, tagged `v2026.294.0021`). The earlier leg measured across four repos that **16 of the 17 image-owned nodes have no local package candy to re-home to**: most images compose only `@github` candies, whose `SourceDir` is a read-only cache in another repo, and `arch`, `debian`, `ubuntu`, `debian-debootstrap` and `ubuntu-debootstrap` compose **zero** candies — so "point `owner:` at a candy the image already composes" is unsatisfiable here. The operator lifted that constraint and authorised option A, naming the precedent: `distro-cachyos` already ships `cachyos-app-skills`, `cachyos-os-skills` and `cachyos-selkies-skills`. This PR creates that candy for this repo.

**The precedent had to be extended, and the measurement is the reason.** The cachyos `*-skills` directories hold skill NODES only — they are not candies, so they cannot be an `owner:` target at all. A candy is required (a `skill:` owner must resolve in the LAYER set), and a candy must have install content (`validateCandyContents` accepts packages, a builder manifest, a `candy:` composition, `data:`, a plugin or an `external_builder`; measured: a check-only plan is rejected with *"must have at least one install file"*). So the bundle is a real package candy that carries the prose INTO the image — `copy: .agents/skills` → `${HOME}/.agents/skills`, the Agent-Skills location a harness inside the image reads — with an ADE `check:` that fails if a body does not land.

**What moves.**

- `charly.yml` → `candy/omarchy-skills/charly.yml`: the 3 routing nodes (`omarchy`, `omarchy-cstream`, `omarchy-vm`), each `owner: omarchy-skills`, with their `family`/`triggers` untouched.
- every body: `git mv` to `candy/omarchy-skills/.agents/skills/<name>/SKILL.md` — **3 of 3 byte-identical**, sha256 pasted below.
- every image that carries one of those skills composes `omarchy-skills`; the `ai.opencharly.skill` label then carries the skills for the first time (the emitted `COPY` and `LABEL` are pasted below).
- the repo rulebook: `AGENTS.md` and `README.md` both said the bodies live at the repo-root `.agents/skills/`; the reader resolves `<candy source dir>/.agents/skills/<name>/`, so both are rewritten from the tree.

**One consequence, stated plainly:** the bundle is ONE candy composed by all 2 images, so each image's label carries all 3 of these skills, not only the one it is named after — the sanctioned single-bundle shape. The base image must compose it for its own skill to reach its own label, and candy composition is inherited along the base chain, so the union is structural rather than a shortcut.

**This PR supersedes #77**, which the validator auto-closed after five counting verdicts. The tree is IDENTICAL to that PR's head (`a1adcd2`) — every code, config and doc byte was already reviewed there — and the only difference is this body: its last surviving finding was a stale sentence claiming `box generate` refuses this tree, written in the rounds when the gate was red and not updated when the gate went green. The sentence now states what the pasted output shows: `box generate` returns `rc=0` and emits the Containerfile with the `COPY` and `LABEL`; no IMAGE BUILD ran, because that needs the imported `arch` base from `ghcr.io`.
