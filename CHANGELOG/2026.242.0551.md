# 2026.242.0551 — fix(ci): pin the build job to a charly that supports the manifest schema

## Summary

The `build` job in this repo's `deploy.yml` has never been able to pass. It cloned charly
`v2026.240.2035`, whose maximum supported config schema is `2026.232.0520`, and every
manifest in this repo declares `2026.240.1943` — so the step that is supposed to be this
repo's own gate failed on schema, not on anything about the manifest:

```
charly: error: command "validate": validation error: charly.yml:
config schema 2026.240.1943 is newer than this charly supports (max 2026.232.0520)
```

That is worse than a missing check: a permanently red `build` on every PR is exactly how a
real failure stops being noticed.

### Root cause

This repo was bootstrapped from a `deploy.yml` template that predates the schema bump. The
two plugin repos in the same cutover were bootstrapped from `plugin-punktfunk`'s corrected
template and carry `v2026.241.1535`; `pod-hyprland`, which already existed, carries
`v2026.241.1130`. Only the repos that took the stale template are affected — 14 of them,
each getting this identical fix.

### Every file in the diff

| File | What changed |
|---|---|
| `.github/workflows/deploy.yml` | the charly pin `v2026.240.2035` → `v2026.241.1535`, and the CI checkout moved from `/tmp/charly` to the workspace-relative `.ci/charly` |

Two changes, both required:

1. **The pin.** `v2026.241.1535` is the newest known-good: it is what the plugin repos in
   this same cutover already carry, and it is the exact version every piece of local
   evidence for this repo was produced with, so CI and local now agree by construction.
2. **The path.** Adopted verbatim from `pod-hyprland`'s corrected workflow, whose own
   comment records why: `actions/setup-go` resolves `go-version-file` and
   `cache-dependency-path` via `path.join(GITHUB_WORKSPACE, file)`, so an absolute
   `/tmp/...` path is joined onto the workspace root and does not exist. Fixing the pin
   without this would move the failure rather than remove it.

## How tested

The pinned charly's schema support was confirmed against the actual constraint before
changing anything — the failing run reports `max 2026.232.0520`, and the manifests in this
repo declare `2026.240.1943`:

```
$ gh run view 33295313980 --repo opencharly/distro-omarchy --log-failed
build  The candy manifest validates at the pinned charly
  charly: error: command "validate": validation error: .../charly.yml: config schema
  2026.240.1943 is newer than this charly supports (max 2026.232.0520). Update charly ...
```

The same `charly box validate` the CI step runs passes locally at `2026.241.1535`, the
version this PR pins — run against this repo's final tree:

```
$ charly/bin/charly box validate
$ echo $?
0
```

The authoritative proof is this PR's own `build` check: the step that has failed on every
previous run against this repo must now be green. That is the gate for this change, and it
runs on the pushed tree rather than on a local reconstruction of it.

```
$ grep -c '/tmp/charly' .github/workflows/deploy.yml
0
```
