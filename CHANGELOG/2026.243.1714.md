# 2026.243.1714 — docs: the upstream test triage, measured rather than asserted

## Summary

The port of `omacom/omarchy@quattro`'s suite into charly beds has a scope boundary, and until
now that boundary lived only in a plan document. This commits it as a table anyone can **re-run
and dispute** rather than take on trust.

**224** entries in upstream `test/shell.d` (the plan said 220; upstream moved) — **223 test
files plus the `fixtures/` directory**, which holds sample inputs for other tests and is not
itself a test. The 223 files are classified by what each can *observe*, using signals in the
file itself:

| Class | Count |
|---|---|
| C — Node/QML unit tests over upstream's source | 39 |
| C — Python scanners over upstream's source | 13 |
| C — other source-level | 89 |
| **B — candidates** (behaviour under test leaves an observable installed trace) | **82** |
| **total classified** | **223** — every test file; the 224th entry is `fixtures/` |

Class C is out of scope on the merits, not only by the live-VM rule: those tests read `$ROOT`,
omarchy's git checkout, and `/usr/share/omarchy/` ships **no `test/`** — running them would mean
cloning upstream's source into the guest, and re-implementing them would duplicate upstream's own
tests (R3) and rot on every release.

The 82 candidates are cross-referenced against the **43** distinct assertion targets this repo's
beds already carry:

| Outcome | Count |
|---|---|
| already covered | 4 |
| gap, mechanically decidable | 21 |
| needs per-file judgement (command surfaces) | 57 |

### A second wrong answer, caught by the validator

The first submission stated 224 entries beside class counts summing to 223, and then claimed
"All 224 entries are classified". The counts were right; the sentence reconciling them was not.
`test/shell.d` holds 223 test *files* plus the `fixtures/` *directory*, and the classification
loop skips non-files — so it correctly produced 223 rows while the prose asserted 224. In a
document whose whole value is reproducibility, an unreconciled total is a defect, not pedantry.
Fixed in `98ee339`, with the three commands that produce the split now in the artifact.

That fix then invalidated this body's own pasted `git show --stat` (233 insertions, the first
commit alone), which the validator caught on the next pass. The evidence block now pastes
`git diff --stat origin/main...HEAD` — the cumulative diff actually under review — because a
per-commit stat goes stale the moment a second commit lands, and a stat that disagrees with the
diff is exactly the failure this PR is about.

### A wrong answer, recorded so it is not repeated

The first cross-reference matched by substring and reported **52 covered / 30 gaps**. It was
wrong: the bed's target list contains `/` — a `mount:` subject — and `/` is a substring of every
path signal, so nearly everything matched. Short name targets (`charly`, `omarchy`, `snapper`,
`limine`) did the same to unrelated tests. The committed numbers use exact path equality, and
command-only signals are reported as **undecided** rather than guessed in either direction. The
rejected method is documented in the table itself.

### Measured, not assumed

The 21 decidable gaps are not equally assertable, and the difference was measured. Probed
read-only over `charly vm ssh` against a freshly rebuilt `check-omarchy-desktop-vm` guest — the
`update` step's rebuild, so a machine built from nothing:

```
PRESENT  /etc/profile.d/locale.sh
PRESENT  /etc/systemd/logind.conf.d/20-inhibit-delay.conf   InhibitDelayMaxSec=15
PRESENT  /etc/vconsole.conf              KEYMAP=us, XKBOPTIONS=terminate:ctrl_alt_bksp
PRESENT  /etc/mkinitcpio.conf.d/omarchy_hooks.conf   HOOKS=(… plymouth … btrfs-overlayfs)
PRESENT  /etc/chromium/policies/managed  but EMPTY — 0 entries
absent   /etc/omarchy.conf
absent   /etc/sudoers.d/omarchy-dev-path
absent   /etc/fido2
absent   /etc/pam.d/omarchy-lock-fingerprint
absent   /etc/modprobe.d/brcmfmac.conf
```

Five are absent **by design** — fido2 enrolment, fingerprint, `dev-link`, brcmfmac hardware — so
asserting them would fail a *correct* guest. And the chromium policy directory exists while
holding nothing, so only its existence is assertable; the obvious assertion (a policy file is
installed) would also fail a correct guest. That is the trap this probe exists to catch, and it
was caught **before** an assertion was written rather than by a red bed afterwards.
