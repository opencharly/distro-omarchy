# 2026.242.2143 — refactor(beds): the omarchy beds assert through typed verbs, not shell

## Summary

**Two** VM beds — `check-omarchy-iso-vm` and `check-charly-omarchy-vm` — move from shell
`command:` steps to typed check verbs. Both are proven end to end below with the full R10
sequence, including the disposable destroy-and-reinstall.

The third bed's conversion was in the first revision of this PR and has been **withdrawn**;
see "Why the pacstrap bed is not here" below. That is the validator's earlier BLOCK acted
on: it objected to three beds changed and one run, and the reason the third could not be
run turned out to be a real defect in its own right.

This is the first unit of porting upstream Omarchy's acceptance suite
(`omacom/omarchy@quattro` `test/acceptance.d/`) onto `check-omarchy-iso-vm`. Converting
what already exists comes first because it needs no new charly capability and it proves the
typed-verb path against a real guest before any new assertions are written on top of it.

## What the conversion buys, beyond "less bash"

- **A per-subvolume `mount:` step names the subvolume that is wrong.** The old form was one
  shell loop over four mountpoints behind `set -eu`, so the first failure hid the other three.
- **Ten `package:` steps replace one `pacman -Q` over ten names**, so a missing package is
  named rather than reported as "some member of a list".
- **`service: {enabled, running}` replaces `test "$(systemctl is-enabled x)" = enabled`**,
  which passes silently on an empty string if systemctl errors.

## Two real defects this found

**1. The subvolume checks could not distinguish the four subvolumes.** They asserted
`contains: subvol=/@`, and `mount:` matches against the whole comma-joined option string
(`plugin-mount/candy/plugin-mount/plugin.go:71-77`) — so that matcher also matches
`subvol=/@home`, `subvol=/@log` and `subvol=/@pkg`. **All four checks would have passed
against any one of the four subvolumes.** They are anchored regexes now
(`subvol=/@($|,)`), which cannot.

**2. Reading a config file is not the same as asking the tool.** The conversion turned the
git-identity check into a `file:` probe of `/home/user/.gitconfig`, and the bed caught it —
`exists=false` against a guest whose identity was correctly applied. Measured on the live
guest:

```
$ ls ~/.gitconfig
ls: cannot access '/home/user/.gitconfig': No such file or directory
$ ls -la ~/.config/git/config
-rw-r--r-- 1 user user 978 Aug 30 20:34 /home/user/.config/git/config
$ git config --global --get-regexp '^user\.'
user.name Charly
user.email charly@opencharly.invalid
```

git's `--global` scope resolves to `$XDG_CONFIG_HOME/git/config` when that file exists, and
`omarchy-settings` ships `/etc/skel/.config` — which the installer copies into the new
account. The check asks git again, and its comment says *do not convert this to `file:`*,
with the measurement, so the next reader tidying up shell does not reintroduce it.

The general lesson is recorded there too: replacing "ask the tool" with "read the file the
tool probably uses" is a regression whenever the tool has search-path logic, because the
check then asserts something narrower than the claim it is named for.

## The bootloader assertion is now two facts instead of a shell correlation

`efibootmgr`'s `BootCurrent` correlated against its Limine entry became:

1. `command: efibootmgr` + `stdout: {matches: 'Boot[0-9A-Fa-f]{4}\*? Limine.*limine_x64\.efi'}`
   — limine's EFI binary is on the ESP and registered;
2. `file: {file: /proc/cmdline, contains: [rootflags=subvol=@, rootfstype=btrfs]}` — the
   running kernel got the command line only limine's config sets.

Together at least as strong, and (2) is the assertion `check-omarchy-pacstrap-vm`'s own RCA
already settled on as stronger than a named-NVRAM-entry test.

## The counts

| Bed | steps | `command:` | typed |
|---|---|---|---|
| `check-omarchy-iso-vm` | 28 | 4 | 24 |
| `check-charly-omarchy-vm` | 5 | 4 | 1 |

`check-charly-omarchy-vm` stays mostly `command:` on purpose — four of its five assertions
are "run this program and match its output", which is exactly what the verb is for. The
gain there is the one step that became `package:`, plus dropping two `set -eu` shell blocks
in favour of asserting the program's own output.

## The 8 `command:` steps that remain, and why each is not a verb

| Step | Why |
|---|---|
| `efibootmgr` | runs a program and matches its output — what the verb is *for* |
| `charly --version` | same |
| `pacman-conf --repo charly Server`, `--repo core Server` | same |
| `git config --global --get-regexp` | asking the tool IS the assertion (above) |
| `pacman -Qo "$(command -v charly)"` | a CORRELATION `package:` cannot express: the deploy also stages a host charly into `/tmp`, so the package can be installed while PATH resolves to the staged copy |
| `sudo -n test -f` on the ESP | `file:` cannot elevate, and the installed ESP is mode 0700 |
| `id -nG user` | **capability gap** — no verb can assert group MEMBERSHIP (`user:` is `{user,uid,gid,home,shell,linger}`, `unix_group:` is `{unix_group,gid}`) |
| `readlink -f /etc/localtime` | **capability gap** — `file:` has `filetype: symlink` but no link-TARGET matcher, and where it points is the assertion |

The last two are capability gaps, not authoring choices. Both are named follow-ups rather
than unexplained shell; `plugin-user` gains `groups:`/`not_groups:` and `plugin-file` gains
`link_target:` in their own PRs, and these two steps convert when those land.

## Why the pacstrap bed is not here

`check-omarchy-pacstrap-vm` does not pass on `main` and has not since it landed:

```
[vm-build] FAIL: vm-build exited 0 but its log carries 1 error line(s);
first at line 1387: ERROR: FAT32 boot partition not found. …
```

The `omarchy` metapackage in that VM's `source.package` pulls limine's alpm hooks as hard
dependencies, and `80-limine-efi-deploy.hook` fires during the pacstrap transaction — where
no ESP is mounted and `/etc/default/limine` does not exist yet, because charly's bootloader
phase writes it afterwards.

Reproduced identically on a charly built **before** the recent plugin-vm pin bump and after
it (same message, same log line), so it is not a regression from this work.

Fixed in `opencharly/plugin-check#11` (**merged**) as a conditional allowance, and with it
the step returns to its historical `[vm-build] PASS ... [allowlisted=4]`. But charly has to
repin that before the bed passes for anyone but me, so claiming the conversion here would be
claiming something a reviewer cannot reproduce. It follows in its own PR.

**Requires `opencharly/charly#497`.** Before that fix `charly vm build omarchy-vm` failed
with `unsupported source.kind "iso"` and this bed died at `[vm-build]` after 637ms — charly
pinned a plugin-vm predating the `iso` arm. All results above are on a `task build:binary`
carrying it.

## Rulebook compliance

- **R1 — RCA every anomaly.** Both the subvolume matcher and the git-identity failure were
  root-caused on the live guest and fixed, not allowlisted or reverted wholesale.
- **R3 — No duplication.** Assertions moved onto the existing shared verbs; nothing new was
  implemented in this repo.
- **R4 — No workarounds.** The two capability gaps are named follow-ups in the plugins that
  own them, not shell that pretends to be a verb. No sleeps: `eventually:` is the only wait.
- **R4a — Fix the product first.** The blocking pin defect is `charly#497`, in charly.
- **R5 — Delete legacy completely.** Every converted step's shell is removed, not left
  beside its replacement.
- **R6 — Git safety.** `git status` inspected; branched from a fresh `origin/main`; no
  force-push, no direct push to `main`, no hook bypass.
- **R7 — Prove the gate, not the plan.** The full R10 sequence is pasted above verbatim.
- **R9 — Binary equals source.** Every result is from a `task build:binary` charly.
- **R10 — Fresh disposable proof.** `check-omarchy-iso-vm` is `disposable: true`; the
  28/28 above is the post-rebuild run.
