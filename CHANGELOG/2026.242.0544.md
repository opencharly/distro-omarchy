### The box is deliberately thin

```yaml
omarchy:
    candy:
        base: arch.arch
        build: [pac]
        platform: [linux/amd64]
        distro: [omarchy, arch]
        candy:
            - '@github.com/opencharly/layer-omarchy-base/candy/omarchy-base:v2026.242.0437'
```

**`base: arch.arch`, not an Omarchy image** — Omarchy publishes no container image, only
an installer ISO. What makes this image Omarchy is the package set and the sources it
comes from, both of which live in `layer-omarchy-base`.

**`distro: [omarchy, arch]` is the tag chain** — an `omarchy:` package section wins where
one exists, and all 99 existing `distro: arch:` candy sections apply unchanged everywhere
else. No candy needs an `omarchy:` section. Same mechanism `distro-cachyos` uses.

**`build: [pac]`, no AUR builder** — all 148 base packages resolve with plain pacman: 23
from `[omarchy]`, 125 from `core`/`extra`/`multilib` served by Omarchy's own mirror
snapshot, 0 unresolvable. Cross-checked against both package databases.

**One pin, four candies.** The box names only the meta; `QualifyRemoteSiblingDeps`
resolves its three members at the same tag across the repo boundary:

```
$ charly box list candies
omarchy-base     [github.com/opencharly/layer-omarchy-base, testing]
omarchy-repo     [github.com/opencharly/layer-omarchy-base, testing]
omarchy-runtime  [github.com/opencharly/layer-omarchy-base, testing]
omarchy-skel     [github.com/opencharly/layer-omarchy-base, testing]
```

**One box-level check, deliberately narrow.** `omarchy-base` asserts everything about the
package sources and runtime, so the box asserts only what is true of the *box* and of no
layer: that the image identifies as Omarchy. `omarchy-settings` **replaces**
`/etc/os-release`, so a built image reports `ID=omarchy` / `ID_LIKE=arch` — not `ID=arch`,
which the first version of this check wrongly asserted and which the bed caught.

That distinction is the evidence for the whole design. `ID=omarchy` is why `omarchy` is
its own `#DistroID` rather than an alias of `arch` (charly's host detection reads that
field, and an image reporting `ID=arch` would be indistinguishable from plain Arch), and
`ID_LIKE=arch` is what makes `hostenv.PopulateTags` emit the arch fallback automatically —
the same chain `distro: [omarchy, arch]` declares at build time. Without it every
`distro: arch:` candy section would stop applying and packages would silently not
install.

### The boot stack is installed but inert

`omarchy` hard-depends on `limine`, `limine-mkinitcpio-hook`, `limine-snapper-sync`,
`snapper` and `sddm`, so a container gets the whole boot/display stack whether it wants it
or not. `layer-omarchy-base` keeps the limine alpm hooks a container cannot satisfy off the
image entirely via pacman `NoExtract`, and no unit is ever enabled. Machine-only surfaces — limine on a real ESP, snapper
subvolumes, plymouth in an initramfs, an sddm seat, uwsm's systemd user manager, ufw's
netfilter tables, dockerd, dkms — belong to the machine images, not to this pod-safe base.

`[check-image]` runs `omarchy-base`'s 16 baked checks against the built image — the
resolved mirror host, the signed key, the absent limine hooks, the package tree, the
seeded home. `[update]` destroys and rebuilds the deploy, and the two `*-rebuild` steps
re-assert against the fresh result, so the box is proven reproducible rather than merely
buildable once.

This bed initially **failed** here, against `layer-omarchy-base` `v2026.241.2341`:

```
[image-build] FAIL: image-build exited 0 but its log carries 2 error line(s);
              first at line 893: FAT32 boot partition not found...
```

That was a defect in the layer, not in this box — the limine alpm hooks were masked
rather than kept off the image, leaving one unsilenceable failure that charly's gate
correctly rejects. Fixed in layer-omarchy-base#2 and pinned here at `v2026.242.0437`.
