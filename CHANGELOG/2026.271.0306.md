# 2026.271.0306 — feat(bed): check-cua-fleet-build-local — the containerDisk produce/publish R10 (plan §3.E.3)

## Summary

Add **`check-cua-fleet-build-local`** — the **PRODUCE-half** R10 bed for the containerDisk path (plan §3.E.3), the consumer the `plugin-vm` `vm bake` work named as its target.

The sibling `check-cua-container-disk-vm` proves the **consume** half (pull + boot a published Cua Fleet containerDisk). This bed proves the other half: charly can **bake** a guest, **emit** the containerDisk, **deliver** it, and **boot the produced artifact** — the full produce→publish→consume round-trip.

### Architecture (redesigned to the entity-vs-deploy rule)

A `kind: vm` ENTITY cannot carry `disposable:` — it is a **deploy** property. So the bed drives two **disposable `vm:` deploys** and keys every VM verb to them via `--domain`:

- **`cua-container-disk-produce`** (`from: cua-container-disk-vm`, `disposable: true`) — the produce deploy. Its per-domain disk is where the **golden** lands and what the bake boots (via the new `vm bake --domain` + `vm create --keep-disk`).
- **`cua-produced-consume`** (`from: cua-produced-consume-vm`, `disposable: true`) — boots the containerDisk the bed itself published.

Nothing pre-existing or shared is destroyed: `cua-container-disk-vm` (the entity, shared with the sibling bed) is only ever **built** (never destroyed); every create/destroy keys a `disposable: true` deploy's domain.

### The host-orchestration mechanism

The produce path is a host-side orchestration (build → golden → bake → emit → push → boot). A bed's own `run:` step is verify-only, so the mutation lives in the bed's own **`check:` steps**, which resolve `${CHARLY_BIN}` (the install-plan lowering does NOT resolve it in a composed candy's `run:` — observed live). Those steps run at BOTH `deploy-add` and `check-live`, so they are authored **idempotent** and carry an explicit `timeout: 3600s` (the probe's never-hang ceiling).
