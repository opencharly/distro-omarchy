# 2026.243.2111 — feat(cstream-pod): the GUI subset, and what it found

## Summary

`check-omarchy-cstream-pod` had **no `plan:` block at all**. Its description — and the
`omarchy-cstream` box's — claimed:

> charly's own `wl:` verb reports hyprland as the live compositor, not a process-list inference

and no `wl:` step existed anywhere in the pod's closure. Searching it returns exactly two
matches: the two sentences making the claim. The supervised-RUNNING half was real
(`layer-omarchy-shell` asserts `service=omarchy-shell` plus a supervisorctl uptime); the
compositor half was prose.

Two assertions close that, as a **fast-feedback mirror** of `check-omarchy-desktop-vm` — each has
a counterpart there, so a pod regression and a VM regression are the same finding at different
cost:

| id | asserts |
|---|---|
| `omarchy-cstream-compositor` | `wl: status` reports hyprland — the promised assertion |
| `omarchy-cstream-monitor` | the nested compositor has somewhere to draw |

The second matters because `gst-wayland-display` is the parent here rather than a physical
output, so an **empty** monitor list is the specific failure this arrangement risks: the desktop
live with nowhere to render.

Both ride in the two host-side verbs via `add_candy`, exactly as the desktop VM bed does. Without
those pins the steps would not fail — they would **skip** as an unknown verb, and a skipped step
reads as not-failed.

## What the other two assertions found — and the fix that followed

`quickshell: ping` and `listPlugins` failed on the first run, and the cause was **not** in this
repo. In that image the Quickshell shell **never started**:

```
launcher     /bin/sh -c ... until [ -e "${XDG_RUNTIME_DIR}/wayland-0" ]
             ... timed out after 60s waiting for ... exit 1
sockets      /tmp/cstream-rt/wayland-1, wayland-2      (NO wayland-0)
qs list --all                 No running instances.
supervisorctl omarchy-shell   RUNNING, uptime 0:00:29 -> 0:00:49   (restart cycle)
```

`layer-omarchy-shell` waited for `${XDG_RUNTIME_DIR}/wayland-0`. Nothing in this stack creates
it: `gst-wayland-display` (the streaming parent) takes `wayland-1` and Hyprland binds `wayland-2`
for its clients. The service timed out, exited 1, and supervisord restarted it forever.

**The existing "supervisorctl shows a stable uptime" check passed throughout**, because what was
stably running is the *wait wrapper*. That is a green assertion proving nothing — and it is why
this bed could have claimed a working desktop while having none.

### Fixed at source, not routed around

The first form of this PR documented the defect and deferred it. The validator blocked that, and
was right on both counts: the deferral named no batch, and the bed would have gone green over a
desktop that had never worked. Both are now closed by merged fixes:

| PR | What | State |
|---|---|---|
| `layer-omarchy-shell#4` | the nested compositor's socket is `wayland-2`, not `wayland-0` | **merged**, `v2026.243.1941` |
| `plugin-quickshell#4` | `runtime_dir:` — a shell registering under its own `XDG_RUNTIME_DIR` | **merged**, `v2026.243.1942` |

The second was a gap in the verb itself: `qs` finds instances through `XDG_RUNTIME_DIR` **and**
filters them by **display**, and the verb could set only the display. Both are load-bearing here
and they fail *differently* — "No running instances" from the wrong dir, "No running instances for
\<config\>" from the wrong display — and neither message names the missing half, which is why the
steps state both rather than discovering them.

### Before and after, same bed

```
quickshell -n -p processes   0 (a wait wrapper only)   ->  1
qs list --all                No running instances.     ->  Instance 9c0enkt,
                                                            display wayland/wayland-2
supervisorctl uptime         0:00:29 -> 0:00:49 cycle  ->  stable
qs ipc ... ping              fails                     ->  ok
```

All four assertions are therefore present and passing, against a desktop that genuinely works.
