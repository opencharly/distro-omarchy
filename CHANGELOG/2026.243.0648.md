# 2026.243.0648 — feat(beds): check-omarchy-desktop-vm — prove the desktop, not just the install

## Summary

`check-omarchy-iso-vm` asserts 52 facts about an unattended Omarchy install and deliberately
never logs in. Those are install-time facts — a guest can have every package, unit and
subvolume right and still fail to draw a bar. Nothing in this repo proved the DESKTOP comes up.

This adds **`check-omarchy-desktop-vm`**: a live user session, the Quickshell shell answering
its own IPC, the layer-shell surfaces mapped and on screen, and the bar's hide/reveal
behaviour — 14 assertions, all through typed check verbs.

It is a separate bed on purpose. A stock Omarchy stops at the sddm greeter and waits for a
human; adding autologin to `check-omarchy-iso-vm` would weaken the one claim that bed exists
to make. Install-time correctness and a working desktop are different claims.

### The assertion `wl: hypr-layers` was built for

Omarchy hides its bar by parking the layer surface off-screen rather than unmapping it, so
that revealing does not force a rebuild. Shown and hidden are the SAME `hyprctl -j layers`
JSON except for coordinates — a check asserting presence passes either way. Measured across
the sequence:

```
omarchy-bar  Virtual-1  0    0  1280  26  onscreen     <- shown
omarchy-bar  Virtual-1  0  -26  1280  26  offscreen    <- hidden: parked at exactly -height
omarchy-bar  Virtual-1  0    0  1280  26  onscreen     <- revealed
```

The surface never leaves the layer list; only `y` moves, by exactly its own height.

## The two defects this PR fixes in itself

The bed's first run was **15 steps, 2 passed, 9 failed, 4 skipped**, and the RCA is the
substance of this PR.

### 1. The setup could never run

All four SKIPs were `run:` steps:

```
SKIP  run enable sddm autologin ...  skipped — verify-only mode (mutating step)
SKIP  run restart sddm ...           skipped — verify-only mode (mutating step)
SKIP  run hide the bar               skipped — verify-only mode (mutating step)
SKIP  run reveal the bar again       skipped — verify-only mode (mutating step)
```

`run:` steps are INSTALL-TIMELINE steps, not deploy-time setup:

- `charly check live` runs verify-only and skips every mutating step (`sdk/kit/planrun.go:300`,
  `pc.VerifyOnly() && step.Mutates()`).
- `charly fleet add` did not run them either — the entire deploy-add log is ten lines of candy
  resolution and a sudo grant, with no plan execution.
- charly's own comment states the intent: *"The install ran at image-build; re-executing it
  against a built/deployed target is redundant."*

So a `from:`-derived VM on a cached image replays them NEVER. The bed was not measuring a
broken desktop — it was measuring a machine nobody had logged into, because the step that logs
in was silently not executed. Confirmed on the live guest before changing anything:

```
$ charly vm ssh check-omarchy-desktop-vm -- ls /etc/sddm.conf.d/
10-theme.conf  10-wayland.conf  99-omarchy-login.conf      <- no zz-charly-autologin.conf
$ charly vm ssh check-omarchy-desktop-vm -- ls /run/user/1000/
bus gnupg keyring p11-kit pipewire-0 ... systemd varlink    <- no hypr
$ charly vm ssh check-omarchy-desktop-vm -- pgrep -a Hyprland
674 Hyprland --watchdog-fd 4 --config /usr/share/sddm/hyprland.lua    <- sddm's greeter
```

**Fix:** the login moves to a candy (`box/omarchy/candy/omarchy-autologin`), which runs on the
install timeline. The account is resolved from uid 1000 rather than hardcoded, following the
`cachyos-kde-settings` precedent, so it composes onto any single-user Omarchy install.

### 2. The bar toggles would have measured nothing

Hide and reveal were also `run:` steps, so under verify-only the three assertions around them
would have measured a bar that was never toggled. A stateful mutate → assert → mutate → assert
sequence cannot be expressed with `run:` in a phase that skips mutation — and
`check-live-rebuild` is exactly that phase. They are now `wl: exec`.

**The desktop bed contains zero `run:` steps.**

## Verified against the guest's own files, not assumed

Read out of the installed disk with guestfish before authoring. Each would have failed the bed
for a reason having nothing to do with the desktop:

- **`omarchy-toggle-bar on` HIDES the bar.** It runs `omarchy-toggle bar-off on`, touching
  `~/.local/state/omarchy/toggles/bar-off`. The argument names the flag, not the bar.
- **`omarchy-shell` hard-fails with "OMARCHY_PATH is not set"** — the guest exports it only
  through the bash rc chain (`env-bootstrap`, which the guest documents as its single source of
  truth), and a charly command step is not a login shell.
- **sddm merges `/etc/sddm.conf.d/*` alphabetically and LATER files win**, so the drop-in sorts
  `zz-`. `99-omarchy-login.conf` sets no `[Autologin]` key, so there is no collision today;
  sorting last means a future distro drop-in cannot take the login back silently.
- The guest ships `grim`, `wtype`, `wl-clipboard` and `hyprctl` — every binary the `wl:`
  methods used here shell out to. It does NOT ship `wlrctl`, and none of these methods need it.

## The add_candy pin is load-bearing

Nothing in this VM's image closure requires `plugin-wl` and the `wl:` steps are authored
inline, so the plugin rides in through the deploy's `add_candy` and the host check runner loads
it — the mechanism `distro-arch` documents for `plugin-spice`.

`v2026.242.2204` is the first tag carrying `hypr-layers` (plugin-wl#7).

**Correction to an earlier revision of this body.** It claimed that without the pin the `wl:`
steps would SKIP as an unknown verb and the bed would report green. That is NOT what happens,
and I had taken it from a comment in `pod-hyprland/charly.yml` rather than measuring it. A/B on
this bed, pin removed and nothing else changed:

```
FAIL  the background layer surface is mapped and on screen
      plugin verb:wl: plugin_input fails #WlInput: #WlInput.method:
      44 errors in empty disjunction  (attempts=120, elapsed=1m59.506s)
15 steps: 7 passed, 6 failed, 2 skipped        ->  FAIL (steps=5)
```

The verb IS served without the pin — the closure reaches `plugin-wl` transitively through
`box/omarchy-cstream -> layer-cstream-desktop -> pod-hyprland` — but at `v2026.240.1326`, whose
`#WlInput` enum holds 44 methods and does not include `hypr-layers`. So the step fails LOUDLY at
schema validation, and the bed fails with it. That is better behaviour than the skip I claimed,
and the pin's justification is the simpler one: it advances the served plugin to a version that
knows the method.

### The multi-version warning, and why it was mine

An earlier revision justified those warnings as org-wide skew this PR "cannot resolve from
here". That was wrong twice over: it was a parking phrase with no named exit, and it was not
even true. Measured A/B on this bed — pin present vs pin removed, nothing else changed — gave
4 warnings vs 0. **This PR's own pin introduced the split**, by meeting an older transitive pin
in the `omarchy-cstream` box.

Traced, and then re-traced, because the first trace was incomplete:

```
box/omarchy-cstream -> layer-cstream-desktop   -> pod-hyprland -> plugin-wl:v2026.240.1326
                    -> layer-omarchy-hyprland  -> pod-hyprland -> plugin-wl:v2026.240.1326
```

Fixing only the first path left the warning standing. Re-resolving the closure and grepping
charly's fetch cache for the pin that was STILL alive surfaced the second path, whose pin lives
in `candy/omarchy-hyprland/charly.yml` rather than the repo-root manifest a first look checks.
A version split is not closed by walking one path to the tail — every path has to arrive, and a
partial repin looks like progress while changing nothing.

Closed as four ordered repins, tail first, each proved before the next:
