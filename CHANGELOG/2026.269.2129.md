# 2026.269.2129 — feat(bed): check-cua-omarchy-vm — the Cua Driver on the Omarchy desktop (GREEN R10)

## Summary of changes

Adds the **driver bed** `check-cua-omarchy-vm` to `distro-omarchy` — the ISO-install half of the
Cua integration. It derives from `omarchy-vm` (the faithful unattended ISO install) plus
`omarchy-autologin` (a stock Omarchy waits at the greeter) and the `layer-cua` candies, and
asserts the driver contract on a real Hyprland session: the daemon is up, its own doctor reports
clean, it exposes its tool catalog, it lists windows, it LAUNCHES a native app and the launched
window appears in its listing, it captures the real desktop as a non-uniform PNG, and the opt-in
**Hyprland plugin is LOADED and ABI-matched**.

This is the follow-up to the GREEN `check-cua-container-disk-vm` bed (distro-omarchy#60): that
bed proves the **consume** half (pull + boot a Cua Fleet containerDisk); this one proves the
**install** half (the `layer-cua` candies on an Omarchy ISO guest) — and both share the driver
contract.

### Why it lands NOW (it could not before)

The plugin-ABI assertion needs the opt-in Hyprland plugin actually LOADED, which required the
**producer fix** in `opencharly/layer-cua#4` (the candy wrote the config include but Omarchy's
`hyprland.lua` never `require`d it). That fix is **MERGED and TAGGED** (`v2026.269.1859`), and
this bed pins `layer-cua:v2026.269.1859` — so the plugin now loads and the assertion passes:

```
PASS  the opt-in Hyprland plugin is loaded and ABI-matched to the compositor  [cua-hyprland-plugin-abi]
```

### Assertions rewritten to what THIS bed composes

The bed's assertions were originally written from Cua's OWN Fleet image (which ships different
apps); this bed composes `omarchy-vm` + `layer-cua`. Measured and corrected:
- launch `nautilus` (a GUI app that keeps its window) — via the schema's `app:` field —
  not the Fleet image's `inkscape`/`omarchy-terminal`;
- assert the `list-windows` JSON shape and the launched window's presence;
- resolve `HYPRLAND_INSTANCE_SIGNATURE` for `hyprctl` (a non-login SSH shell lacks it).

Cua's input tools require a target window (`pid` + `window_id`), which a static plan cannot
resolve at runtime; the bed proves the driver REACHES + OBSERVES a live window and the
isolated-input plugin is loaded+ABI-matched. The window-targeted delivery is exercised by the
sibling `check-cua-container-disk-vm` bed (Cua's own pool targets its app set). The bed's
`description:` states this.
