# 2026.242.1819 — feat(vm): charly-omarchy — the ready-to-run keeper, and its disposable twin

## Summary

Adds **`charly-omarchy`** — the ready-to-run keeper the repo was missing — and
**`check-charly-omarchy-vm`**, the `disposable: true` twin that proves it.

`charly-omarchy` is a **deploy of `omarchy-vm`, not a third template.** A deploy's `from:`
carries deploy-scope fields only (`add_candy`, `install_opts`, `disposable`, `env`, `plan`);
the VM spec — source, disk/ram/cpu, firmware, `ssh:`, `libvirt:` — comes wholly from the named
`kind: vm` entity. So the ISO, the seed and the credentials are stated once, in the entity
that already ships them, and cannot drift between the keeper and what it is a keeper *of*.

It is **not** disposable: it is meant to be kept. The twin is what proves it, so
`charly update` can rebuild the bed from scratch without ever touching an operator's working
guest. The twin derives from the **template**, not from `charly-omarchy` — a bed's `from:`
names a `kind: vm` entity, and `charly-omarchy` is itself a deploy.

## What the bed asserts that `check-omarchy-iso-vm` cannot

That one proves the unattended **install**. This proves the **deploy on top of it**: that
charly can add a package repository, import its key, install a native package and enable its
units in a guest whose pacman is pinned to Omarchy's own frozen mirror snapshot — none of
which is possible without the passwordless sudo established at `prepare-venue` for
`source.kind: iso`.

Four checks, and the fourth is the one worth reading:

| Check | Why it is not redundant |
|---|---|
| `charly` is on PATH and runs | the floor |
| installed as a **native pac package** | the deploy path also stages a host charly into `/tmp` for its own use (`EnsureCharlyInGuest`); a check that only looked for a binary on PATH would pass on that alone. `pacman -Qo` proves the on-PATH one came from the package the layer installed |
| the `[charly]` repo was added | needs `allow_repo_changes` **and** root; this is the assertion those options exist for |
| **Omarchy's frozen mirror survived** | adding a repo by rewriting `pacman.conf` wholesale would silently drop the `Server` lines pinning `core`/`extra` to Omarchy's snapshot, and the guest would start tracking upstream Arch — **a divergence pacman reports success for either way** |

## Writing it found two product defects

Neither is in this repo, both are fixed, and the bed is the only thing that could have found
them:

1. **charly could not install ANY package on an Omarchy guest.** The distro ships
   `00-omarchy-update-guard.hook` (`Operation = Upgrade / Target = * / AbortOnFail`), and
   charly's pac body is mandatorily `pacman -Syu`, so every install is an upgrade transaction
   and every one aborted:
   ```
   Woah partner... This looks like a direct pacman system upgrade.
   error: failed to commit transaction (failed to run transaction hooks)
   ```
   Fixed in `opencharly/charly` by declaring the transaction tool-driven with the guard's own
   documented escape hatch.
2. **Every installer-seed write emitted a non-compliant-volume-id warning** —
   `opencharly/charly#491`, merged.

  around in the bed.

  keeper with no bed is exactly what this PR exists to stop being true.
