# 2026.242.1920 — feat(vm): omarchy-pacstrap-vm — Omarchy built from packages, and its builder

## Summary

Adds the **composable sibling** to `omarchy-vm`: `omarchy-pacstrap-vm`, built by charly's own
machinery from packages, plus the privileged builder it needs and a `disposable: true` bed.

`omarchy-vm` boots Omarchy's own installer ISO and lets Omarchy install itself. This one
pacstraps a rootfs into a partitioned btrfs disk, puts limine on an ESP at `/boot`, and writes
the fstab and unit enablement from charly's own distro templates.

**Two different claims, and both are worth having.** If the ISO path regressed,
`check-omarchy-pacstrap-vm` would still pass; if charly's bootstrap machinery regressed,
`check-omarchy-iso-vm` would still pass. They exercise independent code.

It is explicitly **not** a claim that the result is byte-identical to an ISO install — it is
not. The ISO install runs Omarchy's own orchestrator, which does work charly's bootstrap does
not (snapper configuration, the UKI, the themed limine menu). `check-omarchy-iso-vm` remains
the fidelity proof; this bed proves only that the from-packages path produces a **bootable
Omarchy**.

## The builder's base is the whole design

`omarchy-pacstrap-builder` is built on **`omarchy`**, not on `arch.arch`, and that is the one
decision in this PR that matters.

pacstrap runs *inside* the builder and resolves against the **builder's** `/etc/pacman.conf`.
charly appends a distro's `extra_repo` entries there (`renderPacstrapExtraConf`) but does
**not** rewrite `[core]` and `[extra]`. On a plain-Arch base those still point at upstream
Arch — so the target rootfs would come from a **mix**: the ~23 Omarchy-built packages from
Omarchy's repo and the ~125 `core`/`extra` ones from a newer upstream snapshot than Omarchy
ships. pacman reports success either way, which is what makes that divergence dangerous
rather than merely wrong.

Verified on the built builder image:

```
$ podman run --rm ghcr.io/opencharly/omarchy-pacstrap-builder:2026.242.1824 \
    sh -c 'pacman-conf --repo core Server; pacman-conf --repo extra Server'
https://stable-mirror.omarchy.org/core/os/x86_64
https://stable-mirror.omarchy.org/extra/os/x86_64
```

A plain-Arch builder prints `geo.mirror.pkgbuild.com` there. The box's own check asserts
exactly this, because it is the one claim no composed layer can make for it.

## Two upstream defects this found

Choosing the correct base is what surfaced both. Neither is in this repo:

1. **Every bootstrap VM build in charly was broken** — `charly vm build` of any pacstrap VM
   failed at template render on a field #484 had removed from the schema but left in the
   template. Reproduced identically on `arch-pacstrap`. Fixed in `opencharly/charly#493`
   (merged).
2. **The builder template double-registers repositories** a base image already has:
   ```
   error: could not register 'omarchy' database (database already registered)
   ```
   `charly vm build` still exits 0 and writes the disk, so only a bed's errors-fatal log gate
   catches it — which is how this bed found it. Fixed in `opencharly/charly#494`.

## The plan claim this PR does not carry forward

The plan said `layer-pacstrap-builder` needed `limine` added before this box could exist. It
does not. The omarchy bootloader `install_template` copies `BOOTX64.EFI` from the builder when
present and falls back to the mounted target's copy otherwise:

```sh
cp /usr/share/limine/BOOTX64.EFI {{.Mnt}}/... 2>/dev/null \
  || cp {{.Mnt}}/usr/share/limine/BOOTX64.EFI {{.Mnt}}/...
```

and the target always has it, because `limine` is in omarchy's `pacstrap.base_package`. That
claim was stale; no change to `layer-pacstrap-builder` is needed and none is made.

### Three iterations, three real findings

The bed did not pass first time, and each failure was worth having:

1. **`[vm-build]` failed** on two `error: could not register … (database already registered)`
   lines — the builder template appends repos a base image already has. Fixed upstream in
   `opencharly/charly#494` (merged), not allowlisted here.
2. **`ID=arch`, not `ID=omarchy`.** The rootfs was plain Arch that merely came from Omarchy's
   mirror. My first fix — adding the `omarchy` metapackage — **broke the build**:
   `80-limine-efi-deploy.hook` fires during the pacstrap transaction, before charly's
   bootloader phase writes `/etc/default/limine`, so limine-deploy falls back to `/boot/efi`
   and errors. That is an ordering constraint in the pipeline, not something an entity can
   declare its way out of. The entity is now scoped to what this path can honestly produce,
   and the check asserts the **sources** (`pacman-conf --repo core Server` → `omarchy.org`),
   which is the claim `base: omarchy` actually guarantees.
3. **The limine check asserted the wrong mechanism.** Copied from the ISO bed, it demanded a
   named NVRAM entry; the bootstrap path creates none, because `efibootmgr --create` runs in
   the builder against a loop device. The guest boots limine through the firmware's
   auto-created removable-media entry. Replaced with `/proc/cmdline` carrying
   `rootflags=subvol=@` and `rootfstype=btrfs` — flags that exist only in the `limine.conf`
   charly's template wrote, so a guest booted any other way could not have them. **Stronger,
   not weaker.**

### A note on diagnosing this VM

It is headless by design — `kernel_args: console=tty0 console=ttyS0,115200`, no
`libvirt.devices.video`, matching `arch-pacstrap`. `charly vm screenshot` correctly refuses
and says why:

```
VM charly-check-omarchy-pacstrap-vm was defined with NO video device;
add a libvirt.devices.video (and graphics) block to its kind:vm entity
```

`charly vm console` is the diagnostic for this entity. No video device is added, because a
bootstrap VM does not need a GUI and `omarchy-vm` already covers the graphical case.

## Rulebook compliance

- **R1 — RCA every anomaly.** Three failures were root-caused rather than worked around: the
  template render (charly#493), the duplicate registration (charly#494), and the screenshot
  refusal (correct behaviour for a headless entity, not a defect).
- **R2 — Finish the whole cutover.** The builder box, the VM entity and its bed ship together.
  An entity naming a builder that does not exist would not validate, and a VM with no bed is
  what this repo's previous PR existed to stop being true.
- **R3 — No duplication.** The builder composes the shared `layer-pacstrap-builder` rather than
  restating its toolchain; the VM entity restates none of the distro's `pacstrap.base_package`.
- **R4 — No workarounds.** The two upstream defects were fixed in charly, not allowlisted in
  this bed. Rebasing the builder on plain Arch would have silenced the duplicate-registration
  error and reintroduced the mixed snapshot.
- **R4a — Fix the product first.** Both.
- **R5 — Delete legacy completely.** N/A — additive.
- **R6 — Git safety.** `git status` inspected; branched from a fresh `origin/main`; no
  force-push, no direct push to `main`.
- **R7 — Prove behavior, not compilation.** The builder's mirror resolution is read out of the
  built image; the disk is built and sized; the bed boots it.
- **R8 — Preserve emitted artifacts.** The emitted artifacts are the qcow2 and its seed; both
  are retained above with the rootfs sha256.
- **R9 — Binary equals source.** All builds ran against a `task build:binary` stamped charly.
- **R10 — Fresh disposable proof.** `check-omarchy-pacstrap-vm` is `disposable: true`; result
  appended above.
